# Darwin Evolution SOTA Report — 2026-09-07

TL;DR: `packages/weight-eft/src/reward-hack.ts`'s deterministic reward-hack monitor (an "Ornith-1.0"-style
gate dropping reward-hacked trajectories before SFT/DPO export) scans ONLY the outgoing arguments of an
agent's tool CALLS — never the CONTENT of `role:'tool'` messages (the tool's response). A trajectory that
leaks gold-patch/FAIL_TO_PASS content through an innocuous call (clean arguments, leaking response) sails
through undetected into training data. Disclosed-but-not-fixed last `darwin-evolution` night (2026-09-02,
#272), directly in tonight's SCAN=weight-eft surface. 2026 field evidence (OpenAI's Action-Monitor
baseline, Cursor's/Datacurve's SWE-bench audits) confirms this is a real leak class, not hypothetical.

## MetaHarness Current Capability

`@metaharness/weight-eft` distills Darwin's SWE-bench trajectory archive into SFT/DPO data for a cheap
local model (LoRA). `reward-hack.ts` runs a deterministic, $0 monitor before export, catching 3 kinds of
cheating: gold-path reads, verification-harness tampering, sandbox escapes — but `toolActions()` only
extracts `(tool, args)` from `role === 'assistant'` tool_calls; `role === 'tool'` messages' `content` is
never scanned. The existing fixture's `cheater__cheater-goldread` case happens to ALSO leak the gold path
in its own call arguments (so today's monitor catches it) — but nothing stops a variant where the call is
clean and only the response leaks.

The "None found" cells are not a shrug: no competitor ships anything resembling Darwin Mode's
bounded/sandboxed/archived self-evolution of its OWN harness code (GEPA is the nearest analog and evolves
prompts, not code; Sakana's DGM is the true architectural peer and is research-only). Reward-hack/leak
filtering for self-training data is essentially unaddressed industry-wide — OpenAI documents the problem
but relies on manual grader review. Narrowed to "does any known monitor scan response content, not just
call arguments": OpenAI's own Action-Monitor baseline (Grade A) says yes in principle, but no one surveyed
ships this for RL/self-improvement training-data filtering specifically — a real, field-relevant gap, not a
reinvention.

## Hypothesis

Given a resolved Darwin trajectory whose tool-CALL arguments carry no reward-hack signal but whose
tool-RESPONSE content (`role:'tool'`) contains a gold-read pattern, when `detectRewardHack()` runs over it,
then it should be flagged `kind: 'gold-read'` exactly as a call-argument leak already is today, subject to:
(a) zero verdict change for the 4 existing fixture trajectories; (b) purely additive — no existing pattern,
classification, or finding kind removed/narrowed; (c) 0 regressions in the full `weight-eft` suite; (d) the
new path must be proven non-vacuous (a crafted fixture must fail pre-fix, pass post-fix). Frozen before
implementation, not modified after evaluation begins.

## Evaluation

`evaluated: accepted`. Deterministic, $0, zero LLM calls (candidate is pure logic over trajectory fixtures):

- New fixture: a leak trajectory whose tool-CALL arguments are clean (verified to match none of the three
  pattern lists) but whose tool-RESPONSE content contains `FAIL_TO_PASS: ...`.
- **Pre-fix** (confirmed live via `git stash` on the source change): `detectRewardHack` returns `[]` —
  2/4 new tests fail exactly as predicted.
- **Post-fix**: flags `kind: 'gold-read', tool: 'grep'`; exporter drops the leak trajectory, keeps the
  honest one, no SFT row carries the leaked text. 4/4 new tests pass.
- **Control**: the original 4-fixture archive is byte-identical in verdict — confirmed by the still-green
  original test file and by the critic independently checking every `role:'tool'` content string in it.
- Full suite: **weight-eft 37→41/41** (+4, 0 regressions), `tsc --noEmit` clean. Downstream
  `create-agent-harness`: **572/574** (2 pre-existing skips, unchanged). Monorepo build clean.
- **Independent adversarial critic** (fresh sub-agent, re-ran the suite/tsc itself): **ACCEPT**. Confirmed
  purely additive, fixture non-vacuousness, no false positives on the original archive, no gaming. One
  disclosed non-blocking gap: the scan applies only `GOLD_READ_PATTERNS`, not the other two lists — see
  Recommended Next Steps #1.
