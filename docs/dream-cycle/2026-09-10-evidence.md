## OBSERVATION

- `packages/create-agent-harness/src/repo-scorecard.ts`'s `buildRepoScorecard()` computes the ADR-041
  `toolSafety` dimension from `plan.policy`, and `recommendPlan()` (`analyze-repo.ts`) always assigns
  `policy: SAFE`, a single hardcoded constant, regardless of the repo being analyzed.
- None of the 8 entries in `analyze-repo.ts`'s `ARCHETYPES` ever set `mcp: 'off'` — only `'local'` or
  `'remote'` (the `mcp-server-harness` archetype).
- `genome-scorers.ts::scoreMcpRisk(profile, plan)` (used by the sibling `harness genome` command)
  already computes a 4-way-differentiated 0..1 MCP-exposure signal (`off` / `local_default_deny` /
  `local_permissive` / `remote`) from the exact same `(profile, plan)` inputs `repo-scorecard.ts` has
  available — it was never called from `repo-scorecard.ts`.
- Root `__tests__/harness-score.test.ts` has 2 pre-existing, unrelated failing tests on baseline `main`
  (`d5833dc6`) — a stale 6-key vs. real 7-key `schema` badge-shape assertion, first disclosed by the
  2026-09-08 Dream Cycle night (issue #297 / PR #298, unmerged as of tonight). Confirmed present before
  any candidate change tonight; not touched (different bug class, out of one-conceptual-change scope).

## INFERENCE

- The fix is correctly scoped and directionally verified, not just type-checked: the sign of the
  MCP-exposure deduction was confirmed empirically (higher `scoreMcpRisk().numeric` → lower `toolSafety`,
  matching the dimension's documented intent), not assumed from reading the formula.
- Because every archetype recommends `mcp: 'local'` or `'remote'` (never `'off'`) and `plan.policy` is
  always the safe constant, the achievable `toolSafety` range remains narrower than an ideal fully
  repo-derived signal would produce (now {82, 95, 100} instead of {90, 100}) — a real, disclosed
  limitation of the underlying `recommendPlan()` architecture, not something this one-conceptual-change
  candidate claims to fully solve.
- The 2 pre-existing `harness-score.test.ts` failures and the `analyze-repo.ts` `hasMcp`-detection gap
  (4th sibling of the `.claude/settings.json`-`mcpServers` blindness family) are both real, both
  disclosed, and both deliberately NOT fixed tonight — the first is a different bug class (out of scope
  for a single-conceptual-change diff), the second is deliberately deferred under STEP 1.1's
  duplicate-direction-avoidance learning signal (the same finding shape has already been fixed twice and
  disclosed once in the last 13 nights: 2026-08-28, 2026-09-03/#276, 2026-09-08/#298-pending).

## DECISION

`evaluated: accepted`. Real, reproducible, self-adversarially-critiqued fix to a genuine, previously
undisclosed defect in a user-facing scorecard dimension (`metaharness score`'s `toolSafety`), verified via
non-vacuous red/green proof, 0 regressions across the affected package and the full monorepo (cross-checked
against a true `git stash` baseline), and a live CLI smoke test. Caveats: (1) the achievable `toolSafety`
range is still narrower than ideal because `recommendPlan()` never recommends `mcp: 'off'` — disclosed as
a follow-up, not fixed (would require changing archetype-selection logic, a larger and riskier diff); (2)
the `* 30` deduction-scale constant is a reasonable-continuity choice, not a principled derivation —
disclosed, not hidden.
