# Flywheel Promotion SOTA Report — 2026-09-06

TL;DR: `packages/flywheel/src/sequential.ts`'s anytime-valid sequential-testing gate (an e-process against
repeated-peeking false-commits) was fully built, exported, and unit-tested in 2026 — but had **zero
production call site**. `runFlywheelGenerations` never populated the `pairedOutcomes` field the gate reads
(the type didn't even have it), so wiring `withSequentialEvidence` into a real `FlywheelConfig` always
silently degraded to the plain frozen gate. Wired it into both the live promotion loop and (an independent
critic's own finding, closed same night) `verifyReplayBundle`'s replay re-execution. Same
"documented-but-unreachable safety mechanism" bug class as ADR-278 (2026-09-02, Darwin Mode), different
domain: statistical promotion integrity, not sandbox containment.

## MetaHarness Current Capability

`meetsPromotionRule` (gate.ts) is a frozen, fingerprintable conjunctive gate (primary↑, noopRate↓,
cost≤, ¬regressed, anchor≥). Three prior flywheel-promotion Dream Cycle nights (08-16, 08-26, 09-01)
hardened `verifyReplayBundle` against receipt-splicing, anchor-bypass, and chain-forgery — that surface is
now heavily defended and was deliberately NOT revisited a 4th time tonight. `sequential.ts` sits alongside
the frozen gate as an *injectable* anti-multiple-testing layer, addressing a different risk: a flywheel
peeks at the same holdout every generation, and naive greedy acceptance under repeated peeking has a
published 30-42% false-commit rate (the module's own cited justification). It was real, tested code with
zero path to actually running.

which targets a different point in the pipeline (per-step trajectory verification) than MetaHarness's
per-generation promotion gate. This is a genuine, currently-open gap in production agent-harness tooling —
not (yet) something a competitor solved and MetaHarness missed.

## Hypothesis

Given a `FlywheelConfig` whose Evaluator reports per-item `itemWins` for both baseline and candidate on the
same holdout, when `promotionRule: withSequentialEvidence(meetsPromotionRule)` is supplied to
`runFlywheelGenerations`, then a thin-margin win (few discordant items, e-value below the 1/alpha
threshold) should be REJECTED even though the frozen base gate alone would promote it, and a strong-margin
win (many discordant items favoring the candidate) should be PROMOTED identically to the base gate —
subject to: zero behavioral change for any Evaluator that does not set `itemWins`; `meetsPromotionRule`
itself untouched; the same guarantee must hold under `verifyReplayBundle`'s independent replay, not just
the live run.

## Evaluation

8 new tests (`sequential-wiring.test.ts`), all non-vacuous (confirmed by reverting each fix independently
and re-running):
- THIN evidence (3/20 discordant, e=1.5³=3.375 < threshold 20): frozen gate alone promotes through a REAL
  `runFlywheelGenerations` call (1 promotion); sequential-wrapped does not (0). Pre-fix: both promote (1) —
  test fails as predicted.
- STRONG evidence (20/20 discordant, e=1.5²⁰≫20): both promote.
- Backward-compat: an Evaluator omitting `itemWins` degrades to the base rule through the real run path.
- Same THIN/STRONG pair re-verified through `verifyReplayBundle`'s ADR-235 gate re-execution — pre-fix (on
  `replay.ts` alone), THIN sealed evidence incorrectly re-passes (`gateReExecutes: true`); post-fix,
  correctly fails.

Full downstream sweep, 0 regressions: flywheel 77/77 (was 72/72), evals-math/sql/toolcall/servedmodel/
hle/extract 47/47, autogenous 7/7. `tsc --noEmit` clean. Build: JS/TS only in this sandbox (native
wasm/NAPI steps not attempted — not required for this package).
