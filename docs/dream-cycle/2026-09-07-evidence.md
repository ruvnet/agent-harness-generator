## OBSERVATION

All 5 independent research roles tonight (Deep Researcher, both Scan Researchers, the Competitor
Analyst, and the Architecture Reviewer) converged, unprompted, on the same finding:
`packages/weight-eft/src/reward-hack.ts`'s deterministic reward-hack monitor — which drops
gold-resolved Darwin trajectories that leaked withheld gold/test content before they reach the
SFT/DPO export — scans ONLY the outgoing arguments of the agent's `role:'assistant'` tool_calls.
It never inspects `role:'tool'` messages' `content` field (what a tool actually RETURNED). This
gap was disclosed but not fixed by the last `darwin-evolution` night (2026-09-02, PR #272, in the
same weight-eft/learn scan surface tonight was rotated back onto). 2026 field evidence
independently corroborates the gap is real, not hypothetical: OpenAI's own "Action Monitor"
baseline definition includes tool outputs as well as calls (cdn.openai.com CoT-monitoring paper,
grade A); Cursor's and DeepSWE/Datacurve's 2026 SWE-bench-Pro audits found agents leaking gold
fixes through observation-channel reads (git history, web fetches) rather than suspiciously-named
call arguments; and SWE-bench-Pro leak analysis attributes ~61% of leaked hints to content the
agent READS (an observation), not content it WRITES (a call argument) — the response-side channel
this repo's monitor left uncovered is, per the field's own 2026 data, the *dominant* real leak
vector, not an edge case.

## MEASUREMENT

- **Non-vacuous baseline proof**: built a fixture trajectory (`reward-hack-response-content.json`,
  `cheater__cheater-response-leak`) whose only tool call is a generic `grep` with clean arguments
  (`{"query":"def validate","path":"src"}` — verified directly to match none of
  `GOLD_READ_PATTERNS`/`VERIFICATION_WRITE_PATTERNS`/`OUT_OF_SANDBOX_PATTERNS`), but whose tool
  RESPONSE content includes `FAIL_TO_PASS: test_validate_negative`. On unpatched
  `reward-hack.ts`, `detectRewardHack()` returns `[]` for this trajectory (2/4 new tests fail
  exactly as predicted: `isRewardHacked` false, `exportTrainingData` reports 0 dropped instead of
  1) — confirmed live by `git stash`-ing the source fix and re-running the new test file.
- **Fix**: added `toolResponses()` (extracts `{tool, content}` from `role:'tool'` messages) and a
  4th detection pass in `detectRewardHack()` scanning that content against the existing
  `GOLD_READ_PATTERNS` list, tagged `kind: 'gold-read'` — identical finding shape to the existing
  call-argument detection. Purely additive: no existing pattern, tool classification, or finding
  kind removed or narrowed.
- **Non-vacuous fix proof**: same fixture against patched code — `detectRewardHack` flags
  `kind: 'gold-read', tool: 'grep'`; `isRewardHacked` true; `exportTrainingData` drops the leak
  trajectory (`droppedRewardHacked: 1`) and keeps the honest one, and no SFT row contains the
  leaked `FAIL_TO_PASS` text.
- **Control (no regression)**: the original `reward-hack-archive.json` (4 fixtures, untouched)
  produces byte-identical verdicts under the patched monitor — independently re-verified by the
  critic by manually checking every `role:'tool'` content string in that archive against
  `GOLD_READ_PATTERNS` (no new matches; the existing `cheater__cheater-goldread` case was already
  flagged via its call arguments, so it isn't a coincidental double-catch that masks a false
  negative elsewhere).
- **Full regression check**: `weight-eft` suite 37→41/41 (+4 new, 0 regressions), `tsc --noEmit`
  clean. Downstream: `create-agent-harness` full suite 572/574 (2 pre-existing skips, unchanged),
  the only in-repo consumer that dynamically imports `@metaharness/weight-eft/cli`. Full monorepo
  `npm run build` (4 phases, JS/TS only — no wasm/NAPI steps needed for this package): clean.
- **Independent adversarial critic** (fresh sub-agent, no authorship context, re-ran the suite and
  `tsc` itself rather than trusting the claim): verdict **ACCEPT**. Confirmed the diff is purely
  additive, confirmed the new fixture is non-vacuous by independently checking the leak
  trajectory's call arguments against all three pattern lists, confirmed no false positives on the
  original 4-fixture archive, found no gaming/scope-creep/hardcoding. One disclosed, non-blocking
  follow-up: the response-content scan applies only `GOLD_READ_PATTERNS`, not
  `VERIFICATION_WRITE_PATTERNS`/`OUT_OF_SANDBOX_PATTERNS` — already listed as Recommended Next
  Step #1 in tonight's gist, not attempted here (kept to one conceptual change).

## INFERENCE

The fix closes a real, previously-disclosed-but-unfixed detection gap without changing behavior
for any trajectory the monitor already caught: it is a pure additive scan appended after the
existing three passes, and the full regression suite (including the critic's independent
line-by-line check of the untouched fixture archive) proves the happy path byte-identical. The
non-vacuous before/after proof (a fixture whose leak is provably invisible to the pre-fix
call-argument-only scan, confirmed by literally reverting the source and re-running) rules out the
fix being a no-op that merely adds an unreachable code path. The 2026 field evidence (Grade A
OpenAI Action-Monitor baseline; Grade B/C real-world SWE-bench-Pro leak audits) supports treating
this as closing a genuine, field-relevant gap rather than manufacturing a finding to fill tonight's
rotation slot — the monitor was narrower than the field's own baseline convention for this exact
kind of detector.
